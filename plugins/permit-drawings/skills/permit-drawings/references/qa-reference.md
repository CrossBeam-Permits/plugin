# QA and build reference

The full contract behind `kit-qa.md`: every build output, every QA check and what it fails on, the advisory lists and the preview options. Read the section for a check whose message you do not understand, and the build outputs before packaging.

## Build outputs

`build` writes:

- `build/<set_name>.pdf`: the bound set of drawn sheets. Page labels are the sheet ids. Bookmarks list each sheet.
- `build/<set_name>-with-attachments.pdf`: the drawn sheets and the `attach` PDFs, merged in bound order. The build writes it only when there are attachments and `pypdf` is installed.
- `build/sheets/<id>.pdf`: one PDF per sheet.
- `build/build.json`: the sidecar. It records every placed view, its scale, every text the kit emitted with its bounding box, every claim, every revision cloud, and the SHA-256 of every PDF it wrote (`file_sha256`, which includes the merged set). QA reads it.

Which file to submit: when the set has no attachments, submit `<set_name>.pdf`. When it has attachments and the merged file exists, submit `<set_name>-with-attachments.pdf`. When it has attachments and the build could not merge them (`merged_into` is null in the build output), submit `<set_name>.pdf` and each attached PDF separately, in the positions the build lists.

Before it writes, `build` deletes the outputs that the previous build listed in its `build.json` (the PDFs, the SVG previews and `build/qa.json`) and every PNG in `build/png/`, the preview folder. A removed sheet, an old merged set or an old preview cannot stay behind. Run `qa` and `preview` again after every build. Outside `build/png/`, `build` never deletes a file that the previous `build.json` does not list.

`build` also rebuilds the set twice more, each time in a new Python process with a different `PYTHONHASHSEED`, and compares every file hash. This catches a sheet script whose output depends on the order of a set or dict. `--no-determinism` skips those two rebuilds. Use it only while you iterate. A build you submit, or hand to CrossBeam, must be a full build without `--no-determinism`, so QA can report `determinism: pass`.

## The QA gate

`python3 -m permitkit qa build` prints JSON with `pass`, a status per check, and details. It fails on:

| Check | Fails when |
|---|---|
| `true_scale` | A view's points per inch differs from its label by more than 0.5%, a MediaBox is not the declared sheet size, a page uses a scaling transform (other than the one clip-and-paint block the kit writes for each placed image, counted against the sidecar), the title-block scale disagrees with the views, or a scale bar measured from the PDF disagrees with its view's printed scale. |
| `title_block` | A title-block field does not print its `project.json` value (project title, address, owner, preparer name, date, status label, preparer statement when there is one), or the sheet title, sheet id or scale is missing, or the stamp box is missing. |
| `decimal_inches` | Any kit-emitted text shows a decimal length, such as `5.5"`, `.5"`, `5.5 IN`, `5.5-INCH` or `2.5 FT`. |
| `field_verify` | A printed FV tag is not in the list, or an unverified value prints without its tag. A value with several tags prints them as one run in natural order after the number and its suffix, `33'-7" SEP. FV-1,8,10`; QA reads the run as FV-1, FV-8 and FV-10. |
| `collisions` | Two texts overlap, a text leaves its region or the border, or a text in a view sits on building linework in that view (a wall, a door leaf, a swing arc, a window, a filled poche). A line counts with its stroke width above and below a text. At the ends of a text, a line up to 1 pt wide may touch it. Lines on the annotation layer (dimension lines, leaders, symbols), hatches and light background tints do not count. A filled shape that holds the whole text hides the linework under it: a white window over a wall, or an annotation fill such as an FV tag box, a keynote circle or a white mask. A text on a placed image fails unless a filled shape drawn over the image backs it (a white box). A text placed with `collide=False` is exempt; use that only for a label that belongs inside its symbol. A `build.json` from an older kit has no linework record; the check then warns "rebuild with this kit version" (so do `line_weights`, `hatching` and `grayscale`). The message says where on the sheet the line runs. A line that is not building linework (a setback, a grid line, a leader) belongs on `layer="annot"`. |
| `internal_refs` | A printed text names the drafting workflow instead of the work: the file names `project.json` or `build.json`, `permitkit`, `crossbeam_rules`, the words "the kit", or a question- or decisions-log id such as `Q-012` or `DEC-004`. A reviewer reads the set, not the workflow: write OWNER TO CONFIRM ..., FIELD VERIFY ... or PER ENGINEER instead. FV tags are meant to print and pass. |
| `layout` | A view draws outside its cell. |
| `images` | A placed image's file changed after the build or is missing, an image does not print its source label, a concept rendering lacks its label on the image, or a concept rendering or a photo sits in a drawing view. Warns when an image prints below 100 dpi. `n/a` when the set has no images. |
| `chain_closure` | A dimension chain does not close. |
| `sheet_index` | A printed sheet index differs from the bound order, page labels differ from the sheet ids, or a hand-typed table lists sheets (a panel titled like a sheet index, or a table whose first column holds two or more sheet ids) instead of `sh.sheet_index(panel)`. |
| `claims` | A compliance note rests on an unverified value. |
| `rules` | A drawn value that a `rules` entry in `project.json` names breaks its limit, after QA converts it to the rule's unit (`project-rules.md`, "Rules"). Also fails when the rule cannot be compared (a point value, a unit of another kind). Also fails when the value rests on a `range` of estimates and breaks the limit at every one ("fails even at the best estimate"). It warns, and does not fail, when the value is missing, rests on a PLACEHOLDER, or is or derives from an ASSUMED value that some estimate lets pass. An ASSUMED value is still compared: without a range the message says "would pass" or "WOULD FAIL"; with a range it says "passes at every estimate" or names the end that fails. An ASSUMED value clear of the limit at every estimate (by `check.close`, default 10 % of the limit) passes; near it, it warns (`project-rules.md`, "Estimates near the limit"). A rule with `accepted` reports its FAIL as a WARN that starts `ACCEPTED BY OWNER` (`project-rules.md`, "A design the owner keeps"). A `check.spread` rule compares the largest minus the smallest of its values (`project-rules.md`). `n/a` when the file has no rules. |
| `revisions` | A cloud names a revision that is not listed. |
| `determinism` | The rebuilds in new processes, with different hash seeds, gave different files. A build with `--no-determinism` gets `warn`. |
| `stale` | `project.json`, a `.py` file in a sheet-script folder, or an attached PDF changed after the build. A build that failed leaves the old outputs in place, so this check is what catches QA run on them. |
| `stale_outputs` | The build folder holds a PDF that this build did not write, or a PNG or SVG preview older than this build. |
| `line_weights` | Fails when a true-scale drawing with at least three stroked paths has no line at a cut weight (1.1 pt, `cut_med`, or heavier), so nothing reads as cut. Warns when its heaviest line is less than twice its lightest, so every line reads as one weight (a key plan of walls only can be all heavy on purpose). Draw what the cut passes through with `cut` (thin parts `cut_med`, an elevation outline `profile`), what is seen beyond with `beyond` or `object`, and fine detail with `fine`; dimensions are on the annotation layer and do not count. |
| `hatching` | A true-scale drawing has solid cut lines (the `cut` or `cut_med` width; a dashed line such as a property line is never cut) but no material at all: no hatch and no poche fill. Warns when a material hatched in a view is in no `"hatch:<material>"` legend row anywhere in the set. |
| `grayscale` | A true-scale drawing fills an area in colour. The message gives the grey with the same darkness for each colour. A 3D view, a photo and a finish schedule swatch are not drawings and may be in colour. |
| `view_scale` | Never fails. Warns when a view placed by hand at a fixed scale fits its own cell at a larger standard scale. An architectural scale: pass `scale="fit"` or let `layout.arrange` choose. An engineering scale: `sh.largest_scale(extents, cell, engineering=True)`. A size scale such as `HALF SIZE`: pass the named scale (`FULL SIZE`) to `sh.view`. `scale="fit"` stays architectural, and `largest_scale` has no size family, so neither picks `FULL SIZE`. A view `layout.arrange` placed is never listed: its scale came from its ladder. |
| `connections` | Never fails. Warns for each `connections` entry whose `basis` is still `open` (Building will ask for the maker's tested detail or an engineer's calculation), and for each one no sheet shows with `sh.connection`. `kit-elevations-sections.md`, "Connections that carry a load". |
| `kit_version` | Never fails. It warns when `build.json` records a kit version (`kit_version`) other than the kit that runs QA. Rebuild with this kit. |

With `--out`, `qa` writes the full report to the file and prints a short one: `pass`, the status of each check, the counts, `failed` (the detail lines of each failed check), and `rules` (one line per rule, such as `FAIL  R-2-D2 bedroom door width (<citation>): drawn 30 in ($openings.D-2.width -> $bed_door_w) breaks the rule; it must be at least 32 in`). `failed.rules` holds only the FAIL lines; the `rules` list also holds the WARN and PASS lines. In the full report, `checks.rules.rules` lists each rule with its `id`, `citation`, `value`, `resolved_key` (the value key the reference reached), `drawn` (in the rule's unit), `drawn_text`, `op`, `limit`, `unit`, `value_status`, `range` (the low and high of the checked number over its estimates, or null), its FV tags and its `status`. A spread rule has `spread` and `resolved_keys` in place of `value_status` and `resolved_key`. Read every FAIL and every WARN before a CrossBeam check. A FAIL is a design problem or a wrong reference: fix the design with the owner (`01-scope.md` section 6), or fix the rule entry. Never change a limit to make a rule pass.

What QA measures and what it trusts. QA reads the PDF for the MediaBox, for scaling transforms, for page labels, and for each scale bar: it finds the bar's printed foot numbers and the view's printed scale label in the PDF content and checks the spacing against the label. QA does not measure view geometry in the PDF. The scale of each drawn line comes from the kit's one mapping from real inches to points, with no transform in the page; QA checks that mapping as the sidecar records it. Unit tests cover the mapping itself. So a hand-edited `build.json` can hide a false view scale from QA, but not a false scale bar.

### The measure list

`python3 -m permitkit measure project.json --out questions/measure-list.md` lists every open field-verify tag: one with no `signed_off` whose values are not all measured (a tag that lists no `values` stays open until it is signed off) in the order the owner should tape them: first the tags a `rules` entry rests on whose drawn number breaks the rule, then the tags any rule rests on, then the tags printed on the most sheets (read from `build/build.json`, or `--build <folder>`), then the `rank`. It prints JSON (`items`, `untagged`: PLACEHOLDER values with no tag) and writes a markdown table for the owner. It changes nothing and never fails.

### Advisory list

`advisory.unverified_text` lists every note or label that prints an unverified value or an FV tag, with its sheet, its text, its unverified keys and its tags. It never fails QA. Read every entry before you hand the set on. If an entry states or implies that the work complies (COMPLIES, MEETS, OK, SATISFIES, or the same idea in other words), rewrite it: state the requirement and the FV tag, or measure first. This is your judgment. The kit does not pattern-match claims.

`advisory.conditional_code_notes` lists every note whose `cd=` ID (for example `CD-014`) is one that `code_notes` in `project.json` marks with `conditions: true`. Each entry gives the sheet, the text, the IDs and each entry's `note`. `not_printed` lists marked IDs that no printed note records. The list never fails QA. The kit matches only the recorded ID, never the printed text. A note written as a plain string has no `cd`; write it with `kit.text`. Read each note against its entry in `logs/code-decisions.md`. The note must print the condition with the limit, or the branch and the fact that selects it (`05-code-questions.md` section 6). A "not required" note must address every trigger the answer named (section 7 there).

`advisory.sheet_fill` gives, for each sheet, the share of the drawing area that holds a view, a panel, a slot or text (`used`, 0 to 1) and the tallest empty strip across it (`empty_band_in`). `low` lists each sheet under half used; the short `--out` report prints them as `sheet_fill_low`. It never fails QA. Look at each listed sheet in the preview and fill it (`kit-sheets.md`, "Composition rules": a larger scale, a bigger cell, or panels that take the space the others leave), or say in your report why it stays as it is.

QA also lists every code citation string on the sheets, grouped by the note it sits in (`citations.groups`) and by section (`citations.by_reference`). The kit only extracts them. A number with a unit word after it (`50.59 SQ FT`, `12.9 DEG`) is not listed, nor a bare number that is the printed value of a key the note records (`RAKE {rake:n}`). Read the list and check that the same topic cites the same section and edition everywhere, against CrossBeam or the primary text.

## Previews

`preview` writes `build/png/<id>.png`. Options: `--sheet <id>` (repeat for more) renders only those sheets; `--out <folder>` writes somewhere else inside the project folder (a folder outside it is refused); `--prefix <text>` starts each file name and may not hold a path separator or `..`. Every build clears `build/png/`. A picture you send to the owner goes in `questions/` with `--out questions --prefix Q-<id>-` (`asking-the-owner.md` section 2). Outside `build/png/`, `preview` refuses to overwrite a file. It checks each target file by its real path. On macOS it uses Apple's renderer (`sips`), because poppler on macOS shows the built-in Helvetica-Bold as regular. Elsewhere it uses `pdftoppm` when present. With neither, build with `--svg` and open the SVG files. For a zoomed look, render one sheet larger:

```
sips -s format png build/sheets/A-2.pdf --out build/png/A-2-zoom.png -Z 5400     # macOS, about 150 dpi
pdftoppm -r 150 -png -singlefile build/sheets/A-2.pdf build/png/A-2-zoom          # elsewhere
```
